# Крок 4.3 — екрани. Повна специфікація

Виконується після 4.1 (токени, шрифти) і 4.2 (каркас). Це технічне завдання, а не
опис напрямку: тут навмисно немає місць, де треба щось вирішувати самому.

Візуальний орієнтир — `prototype.html`. Що не має загубитись — `01-inventory.md`.
Термінологія — `00-plan.md`, розділ «Словник». Правила — `CLAUDE.md`.

> Документи в `docs/admin-redesign/` веде окрема сесія (Cowork), яка пише прямо в
> репозиторій. Незакомічені зміни в цій теці — навмисні, це правки автора ТЗ, а не
> залишки роботи. Їх треба комітити разом із поточним екраном, не відкочувати.
> Якщо правка суперечить тому, що вже зроблено в коді, — сказати про це, а не
> мовчки привести документ у відповідність.

## Протокол виконання

Іти екранами в порядку нижче. Для **кожного** екрана цикл однаковий:

1. Прочитати відповідний розділ `01-inventory.md` — там вичерпний перелік дій, які
   мають вціліти.
2. Розібрати екран на `pages / components / hooks / model` за зразком
   `features/orders-rental`.
3. Перевести на `features/admin/ui` і токени. Прибрати `import './Admin.css'`,
   inline `style={{}}`, `alert()`, `window.confirm()`.
4. `npm run build` і `npm run lint` — обидва чисті.
5. Окремий коміт: `admin: redesign <екран>`.
6. Наступний екран без питань.

**Зупинитись і спитати** тільки в трьох випадках:
- потрібні дані, яких немає в API, і незрозуміло, звідки їх брати;
- дія з `01-inventory.md` не має місця в новому макеті;
- зміна зачіпає БД поза списком у розділі «Сервер» нижче.

**Контрольні точки** — після Складу, після Угоди і після Каталогу зупинитись,
коротко написати, що вийшло, і дочекатись відповіді. Решту робити поспіль.

### Сервер — повний доступ

Половина проблем поточної адмінки — від того, що екран вантажить увесь каталог
заради клієнтського пошуку. Тому сервер переробляти можна і треба: нові поля у
відповідях, нові ендпоінти, серверні пошук/фільтр/пагінація, індекси, транзакції,
перенесення обчислень із клієнта в БД, міграції зі зміною схеми.

### Що означає «зберегти функціонал»

Зберігати треба **задачу, яку функція виконує для бізнесу**, а не її поточну
механіку. Механіку можна й треба спрощувати.

Критерій: після зміни користувач досягає того самого результату — не обов'язково
тими самими кліками. Прибрали спосіб — покращення. Прибрали можливість — втрата.

Дозволено без питання:
- звести три способи змінити залишок до одного;
- замінити клієнтську фільтрацію серверною;
- об'єднати дві сутності, якщо користувач ніколи не працює з ними окремо
  (саме це відбувається з угодою і заявкою оренди);
- замінити ручне поле обчислюваним;
- переписати функцію інакше, якщо так вона простіша й надійніша.

**Спитати перед тим, як робити:**
- видалення будь-яких даних користувача (не коду) — карток, клієнтів, подій, історії;
- зміна формату документів, що йдуть клієнтам: рахунки, договори, акти, протоколи;
- зміна нумерації угод і документів;
- прибирання поля, яке хтось міг заповнювати.

### Робота з базою — обов'язковий протокол

**Зроблено, це поточний стан.** `server/.env` містить бойовий `DATABASE_URL`
(Railway), але `server/config/db.js` і `config/sequelizeConfig.js` читають його
лише за явного `ALLOW_PROD_DB=1`. Без прапорця `npm run dev`, `npm run migrate`
і всі `server/scripts/*` йдуть у локальний `pp_shop_dev`; персональні креденшели —
у гітігнореному `server/.env.local`, який має пріоритет над `.env`. Безпечно за
замовчуванням: щоб зачепити продакшен, треба зробити це навмисно.

**Для кожної міграції**, у такому порядку:

```
cd server
npm run db:backup        # pg_dump → server/backups/backup-<timestamp>.sql
npm run db:snapshot      # зліпок кількості рядків ДО
npm run migrate
npm run db:verify
npm run db:snapshot      # зліпок ПІСЛЯ — порівняти з попереднім
```

`npm run db:backup` потребує `pg_dump` у PATH (у Windows це PostgreSQL Command Line
Tools). Якщо його немає — не пропускати крок, а зробити резервну копію інакше:
`npm run db:export-json` (чистий node, працює завжди) **плюс** знімок у Railway →
Postgres → Backups → Create backup.

Кожна міграція має робочий `down`. Перевірити його одразу: `npm run migrate:undo`,
переконатись, що схема повернулась, і накотити знову. Міграція без перевіреного
відкоту не вважається зробленою.

`ALLOW_PROD_DB=1` додається перед конкретною командою, ніколи не глобально в `.env`,
і тільки після явного підтвердження користувача в переписці.

### Викочування на продакшен

Редизайн змінює словник статусів угоди, тому код і база мають переїжджати разом.
Поки цього не сталося, продакшен живе на старому словнику, а гілка `admin-redesign` —
на новому. План викочування, коли дійде:

1. Бекап продакшену (`db:backup` + знімок Railway) — не пропускати, навіть якщо
   міграція виглядає безпечною.
2. Коротке вікно, коли сайт не приймає нових замовлень: між міграцією бази і
   деплоєм коду не має з'явитись замовлення, записане старим словником.
3. Спочатку міграція бази, потім деплой сервера, потім клієнта.
4. Одразу після — перевірити: список угод фільтрується за кожним статусом,
   у жодної угоди не порожній бейдж статусу, нове замовлення з публічного сайту
   створюється і має статус `new`.
5. Тримати напоготові `migrate:undo` і попередній деплой.

`getStatusMeta` повертає сирий рядок із нейтральним тоном для невідомого статусу,
тому неспівпадіння словників не покладе адмінку — але зламає фільтри й ланцюжок
стану. Це деградація, а не захист: розраховувати на неї не можна.

## 1. Склад — `/admin/stock`

Найбільший виграш, тому перший. Вкладки: `Залишки` · `Журнал` · `Склади`.

### 1.1 Залишки

Над таблицею — сегментований перемикач складів (`warehousesApi.list()`, активний
запам'ятовується в `localStorage`, як зараз). Під ним тулбар: пошук
«Назва, SKU, інв. №, серійний…», селекти `Стан`, `Категорія`, `У каталозі`,
праворуч основна кнопка `Новий інструмент`. Усе — у query-параметрах через
`useUrlState`.

**Рівно шість колонок.** Це головна вимога екрана.

| Колонка | Зміст |
|---|---|
| Інструмент | мініатюра 34×34 + назва + рядок `інв. № · SKU` моно |
| Стан | `StatusBadge` з `stock/model/stockStatus.js` |
| Кількість | кластер із трьох чисел: **на складі** · **в оренді** · **вільно** |
| Ціна / доба | моно, вирівняно праворуч |
| У каталозі | `Показано` / `Приховано` |
| | шеврон |

Кластер «Кількість» — те, заради чого все затівалось. Три числа в одній комірці,
кожне з підписом під ним (`--ds-text-xs`, uppercase, `--ds-text-subtle`), моно з
`tabular-nums`. «вільно» = 0 → колір `--ds-danger`; «вільно» > 0 → `--ds-success`.
Ніяких колонок `Резерв`, `Мін.`, `Всього од.` у таблиці — вони переїжджають у панель.

Клік по рядку → бічна панель (`Drawer`). Чекбокси лишаються окремою колонкою.

### 1.2 Панель позиції

Замість модалки `WarehouseProductWorkModal`. Структура згори вниз:

1. **Шапка** — мініатюра, назва, рядок `інв. № · SKU · <склад>`, кнопка закриття.
2. **Чотири числа** в рядок: на цьому складі · в оренді · вільно · всього по складах.
   Остання — сума по всіх складах; саме її плутанина з «К-сть» була джерелом помилок,
   тому підпис має бути повний, не «Всього од.».
3. **Дії** — сітка 2×3, усі однакової ваги:
   `Перемістити` · `Відправити в ремонт` · `Змінити кількість` ·
   `Картка в каталозі` · `Прибрати з сайту` / `Повернути в каталог` ·
   `Списати зі складу` (єдина деструктивна, `--ds-danger`).
   Для позиції зі станом «на ремонті» замість `Відправити в ремонт` —
   `Повернути з ремонту` з вибором складу призначення.
4. **Зараз в оренді** — список угод: `Угода <номер> · <клієнт>` + пілюля з датою
   повернення або `прострочено`. Веде на `/admin/deals/:id`, **не** на старий
   маршрут заявки.
5. **Картка** — `dl`: серійний №, технічний стан, комплект, вартість заміни, застава,
   вага, мін. залишок. Мін. залишок редагується тут.
6. **Останні події** — три останні з журналу по цій позиції.

Виправити по дорозі:

- **`Відправити в ремонт` зараз в інтерфейсі немає взагалі**, хоча
  `inventoryApi.moveToRepair` існує. Додати.
- **Ремонт прив'язаний до назви складу `'У ремонті'`** — перейменування складу тихо
  ламає функціонал. Перевести на `stockStatus` позиції.
- **Кількість, резерв і мінімум зберігаються по-різному**: кількість просить
  підтвердження, решта зберігається мовчки. Однаково через `ConfirmDialog` з текстом
  «`<назва>`: X → Y. Підтвердіть зміну.»
- **Масове переміщення йде циклом послідовних запитів**; падіння на середині лишає
  половину перенесеною без відкату. Зробити один серверний ендпоінт, що приймає
  список і виконує в транзакції.

Масові дії — плаваюча панель знизу: `Обрано: N` · `Перемістити обрані` ·
`Очистити вибір`.

**Готово, коли:** таблиця вміщується без горизонтальної прокрутки на 1440px; усі дії
з `01-inventory.md` (розділ `AdminWarehousePositions` + `WarehouseProductWorkModal`)
доступні; жодного `window.confirm`.

### 1.3 Журнал

Колонки: `Час` (моно) · `Дія` (чип) · `Що сталось` · `Хто`.
Фільтри: **тип дії** (зараз його немає, хоча типи в даних є), склад, користувач,
дати від/до. Кнопка `Експорт`.

Рядок «Що сталось» будується структуровано з полів події, а не з готового `message`:
`<товар> · <кількість> · <звідки> → <куди>`. Назва товару — посилання на його позицію.

### 1.4 Склади

Сюди переїжджає черга з видаленого `/admin/admin`.

Таблиця: `Склад` (назва + адреса/нотатка) · `Позицій` · `Одиниць` · `Стан` · `Дії`.
Склад із запитом на видалення — рядок підсвічений `--ds-warning-soft`, у діях
`Підтвердити` / `Відхилити`, `Підтвердити` через `ConfirmDialog` з наслідком
(скільки позицій на складі і що з ними буде). Службові склади (`Основний склад`,
ремонтний) — пілюля `Службовий`, без дій.

Над таблицею банер, коли є запити: «N запитів на видалення складу чекають рішення».

## 2. Угода — `/admin/deals/:id`

Другий за важливістю: це екран, у якому проходить робочий день.

**Шапка:** `← До списку`, номер угоди моно `--ds-text-xl`, чипи `оренда` / `магазин`,
під ними `Створено <дата> · <клієнт> · <юрособа>`. Праворуч індикатор
`Збережено` / `Є незбережені зміни` і `Зберегти`.

**Ланцюжок стану** замість двох селектів: `Новий → Рахунок → Оплачено → Видано →
Повернуто → Виконано`. Пройдені — галочка й `--ds-success`, поточний — акцент,
майбутні — приглушені. Клік по кроку змінює статус через `ConfirmDialog`, якщо
крок назад. Кроки `Видано` / `Повернуто` показуються тільки для угод з орендою.

**Три колонки** (`1fr / 1.35fr / 0.85fr`, на вузькому — в одну):

*Ліва:* картка `Клієнт / Орендар` — поля з пілюлею `З бази` / `Немає в базі` +
кнопкою прив'язати чи створити; відповідальні особи; кнопки `Відкрити картку`,
`Редагувати`. Нижче картка `Доставка та оплата`: продавець, доставка, оплата, час
видачі, застава.

*Центральна:* `Позиції`. Орендний рядок показує `інв. № · с/н · кількість ·
<дата> → <дата> · N діб`, під ним рядок `Комплект: … · Стан: …`. Товарний —
`SKU · кількість × фасування = підсумок`. Підвал: Підсумок / Знижка N % / у т. ч.
ПДВ / **Разом**.

*Права:* `Документи` в порядку виникнення:
`Рахунок` → `Рахунок на заставу` → `Договір оренди` → `Протокол (Додаток №1)` →
`Заявка оренди` → `Акт повернення-огляду`.
Документ, для якого ще немає підстави, — неактивний з поясненням («доступний після
видачі»), а не однакова кнопка `Сформувати`. Сформований показує версію й дату,
іконки «сформувати заново» і «завантажити», список версій, що розгортається.
Видалення версії — через `ConfirmDialog`.

Виправити:

- **Заявка оренди перестає бути окремим екраном.** `RentalApplicationEditor` у
  режимі `enrichmentOnly` вбудовується в позиції: серійники, стан, комплект
  редагуються прямо в рядку позиції. Сім булевих пропів режиму
  (`embedded`, `hideHeader`, `hideToolbarSave`, `hideDocumentTab`, `hidePartiesTab`,
  `enrichmentOnly`, `discountLocked`) прибрати — лишається один компонент, один режим.
- **Заявка створюється автоматично**, щойно в угоді з'явилась позиція з каталогу
  оренди. Не кліком по заголовку згортайки.
- **Одна кнопка `Зберегти` шле два послідовні запити** без відкату. Зробити один
  серверний ендпоінт, що зберігає угоду й заявку в транзакції.
- **Дати оренди вводяться двічі** — у позиції й у заявці. Джерело істини — позиція.
- **Дані клієнта в трьох місцях** (угода / заявка / база). Джерело — прив'язаний
  клієнт; поля угоди заповнюються з нього і не редагуються окремо, поки прив'язка є.

## 3. Угоди — `/admin/deals`

Вкладки `Всі` · `Магазин` · `Оренда` · `Календар` з лічильниками; активна в URL.

**Список.** Колонки:
`№ / дата` (номер моно, під ним дата) · `Клієнт` (ПІБ + телефон моно) ·
`Позиції` (чипи типу + короткий опис) · `Сума` (моно, праворуч) · `Статус` ·
`Оренда до` (моно; прострочено — `--ds-danger`).

Клік по рядку → угода. Одна основна кнопка `Нова угода` — на всіх вкладках однаково.

Тип угоди (`магазин` / `оренда`) **приходить із сервера полем**, а не рахується на
клієнті завантаженням усього каталогу. Пошук, фільтр і пагінація — серверні.

**Календар.** Те, що вже зроблено, лишається; доробити три речі:

1. **Назва інструмента в рядку.** Зараз більшість рядків показує лише код
   (`PP-T8H8Q`), назву — одиниці. Рядок має бути `назва` + під нею `інв. №` моно.
   Причина, найімовірніше, у тому, що подія календаря не несе назву — додати її на
   сервері, а не тягнути весь каталог на клієнт.
2. **Кількісні позиції** (`trackingMode = 'quantity'`, див. «Модель даних») —
   один рядок замість двадцяти чотирьох: у кожній комірці дня вертикальна шкала
   заповнення й підпис `16/24`. Заповнення < 60 % — `--ds-info`, до 90 % —
   `--ds-warning`, вище — `--ds-danger`.
3. **Групи за категорією** — рядок-заголовок з лічильником `N з M зайнято` і смугою
   завантаження у відсотках, згортається. У режимі `За категоріями` всі згорнуті.

## 4. Каталог — `/admin/catalog`

Вкладки `Інструмент` · `Товари` · `Категорії та бренди`.

Над вкладками — постійна плашка: каталог відповідає за **картку**, склад — за
**кількість**.

**Інструмент.** Колонки: `Картка` (мініатюра + назва + SKU) · `Категорія / бренд` ·
`Тариф` (ціна за добу + `від X за 7+ діб`) · `Вільно` · `На сайті` · `Фото`
(кількість або `немає` червоним).

Прибрати:
- поділ на «нормальні» й «нульові» картки двома списками — один список і фільтр
  `Вільно: всі / є / немає`;
- пояснювальний абзац про те, чого тут не можна зробити;
- кнопку `Додати зі складу` — тут просто `Нова картка`.

**Товари.** Колонки: `Товар` · `Категорія / бренд` · `Ціна` · `Залишок` · `Мітка`.
Прибрати хардкод `CATEGORY_OPTIONS` — категорії з `categoriesApi`. Рядок клікабельний
(зараз ні, на відміну від усіх інших списків).

**Картка** (`ProductEdit`) — розібрати простирадло на вкладки:
`Основне` · `Ціни` · `Фото` · `Характеристики` · `Оренда` (тільки для інструмента).
Кнопка збереження закріплена в шапці, попередження про незбережені зміни при виході.
**Прибрати звідси редагування залишку** (`editWarehouseQuantity`) — залишок живе
тільки на складі. Правило «Підвіконня → матриця цін» перевести з назви категорії на
прапорець категорії.

**Категорії та бренди.** Група категорії оренди — селект зі списку наявних груп плюс
«створити нову», а не вільний текст у кожному рядку. Категорії магазину дістають те
саме, що й орендні: перейменування і прапорець видимості. Підтвердження видалення
показує, скільки карток у категорії.

## 5. Клієнти — `/admin/clients`

**Список.** Колонки:
`Клієнт` (ПІБ + другий рядок: адреса майданчика або текст претензії) ·
`Телефон` (моно) · `Знижка` · `Угод` · `Оборот` · `Стан`.

`Стан` — пілюля: `Прострочена оренда` (danger) / `Оренда активна` (info) /
`Претензії` (warning) / `Без активних` (neutral).

`Угод`, `Оборот` і `Стан` — **агрегати з сервера**. Зараз їх видно лише всередині
картки; саме тому список ні про що не говорить.

Три іконкові кнопки в колонці `Дії` прибрати: рядок клікабельний, дії — у картці.
Зараз рядок клікабельний і водночас містить кнопки зі `stopPropagation` — постійні
промахи.

Фільтр: `Всі` / `З претензіями` / `Зі знижкою` / `Активна оренда`.

**Картка.** Шапка: ПІБ, `#id`, `клієнт з <дата>`, пілюлі знижки й претензій, кнопки
`Редагувати` та `Нова угода`. Далі: `Контактна інформація`, `Статистика`,
**одна історія угод** (оренда й магазин разом, з чипом типу — не дві незв'язані
таблиці), `Нотатки`, `Претензії`.

Форма клієнта — **тільки** `ClientFormModal`, той самий компонент у списку й у картці.
Зараз форма продубльована, а `saveNotes`/`saveClaims` шлють весь об'єкт клієнта
(`{...client, notes}`) і можуть затерти поля застарілим станом — слати лише змінене
поле.

## 6. Компанія — `/admin/company`

Вкладки `Користувачі` · `Підрозділи` · `Юрособи`.

**Користувачі.** Рядки зі статусом `Очікує` — угорі, підсвічені. Роль призначається
селектом і кнопкою `Схвалити` — **тими самими назвами, що в `ROLE_LABELS`**. Зараз
роль називається трьома способами: `Оренда` в кнопці схвалення, `Менеджер оренди` в
селекті, `ПАН ПІВДЕНЬБУД` / `Пан Південьбуд` у різних місцях. Єдине джерело —
`ROLE_LABELS`. Кнопку `Відхилити`, яка фізично видаляє користувача, перейменувати на
`Видалити` і показати наслідок. Додати пошук і фільтр за роллю та статусом.
Легасі-роль `manager` прибрати міграцією.

**Підрозділи.** Таблиця: `Підрозділ` · `Голова` · `Людей` · `Табель за <місяць>`
(`Збережено <дата>` / `Не збережено`) — зараз дізнатись, хто здав табель, можна лише
відкривши кожен місяць руками. У діалозі видалення показувати наслідок: голова
втратить роль.

**Юрособи.** Новий екран: CRUD над довідником орендодавців. Поля з
`constants/sellers.js`: назва, ІПН/ЄДРПОУ, адреса, блок `rentalLessor`, прапорець
ПДВ, «за замовчуванням». Після переїзду в БД константу видалити, а всі місця, що її
читають (друковані форми, розрахунок ПДВ, блок «Сторони»), перевести на API.

## 7. Табель — `/admin/timesheet`

Прибрати таб-бар з одного елемента. Час вводиться **одним полем `08:30`**, а не двома
по два символи (зараз до 62 інпутів на людину за місяць). Додати колонку `Годин` —
табель наразі нічого не рахує. Попередження про незбережені зміни при зміні місяця
чи року. `alert('Табель збережено')` → тост. Експорт для власника блокується, поки не
обрано конкретний підрозділ, а не падає помилкою після кліку.

## 9. Робочий стіл і залишки каркаса — `/admin`

**Цей розділ дописаний пізніше: у первинній версії ТЗ його не було.** Робочий стіл
описаний у `00-plan.md` і в прототипі, але в переліку екранів кроку 4.3 випав, тому
досі тримає `Admin.css` і виглядає по-старому. Це головний екран — те, що бачать
першим щодня, — і саме через нього `Admin.css` не вдається видалити.

### 9.1 Робочий стіл

Не вітрина цифр, а список того, що потребує дії. Дві колонки (`1.9fr / 1fr`, на
вузькому — в одну).

**Ліва колонка — картка «Потребує уваги».** Рядки, кожен: кольорова смуга ліворуч
(`--ds-danger` / `--ds-warning` / `--ds-info` / `--ds-neutral`), заголовок, другий
рядок із деталями, праворуч підпис куди веде. Увесь рядок клікабельний і веде туди,
де це вирішується — не на загальний список.

Джерела рядків:

| Рядок | Умова | Веде на |
|---|---|---|
| Оренда прострочена | позиція угоди, `rentTo` < сьогодні, статус не `returned`/`cancelled` | `/admin/deals/:id` |
| Повертаються сьогодні | `rentTo` = сьогодні | `/admin/deals?due=today` |
| Запит на видалення складу | є непідтверджені запити | `/admin/stock/warehouses` |
| Нові користувачі | `status = 'pending'` | `/admin/company/users` |
| Мало вільних | вільно ≤ `minStock` | `/admin/stock?status=low` |
| Угода без рахунку | статус `new` понад 3 доби | `/admin/deals/:id` |
| Картки без головного фото | немає `image` | `/admin/catalog/tools` |

Порядок: критичні → попередження → інформаційні → нейтральні; усередині групи —
за датою. Порожній стан — не порожня картка, а рядок «Усе під контролем».

**Права колонка — два блоки чисел**, кожне число моно з `tabular-nums`:

- `Сьогодні · <дата>`: Видати інструмент · Прийняти назад · Активних оренд ·
  В оренді на суму.
- `Магазин · <місяць>`: Замовлень · Оплачено · Виручка.
  **Скасовані угоди не рахуються** — поточний дашборд рахує їх у виручці.

**Сервер:** один ендпоінт `GET /api/admin/dashboard`, що віддає готові рядки й
числа, з урахуванням ролі. Зараз дашборд вантажить увесь список товарів і всі
замовлення на клієнт заради підрахунку кількостей — так не має бути.

**Ролі:** менеджер оренди бачить лише орендні рядки й блок «Сьогодні», без блоку
магазину. Окремого `RentDashboard` більше немає — це один екран із різним наповненням.

**Видалити:** `pages/admin/RentDashboard.jsx`, `pages/admin/AdminWarehouseHome.jsx`
(замінений вкладкою «Склад → Головна» ще на кроці 1, лишився мертвим).

### 9.2 Дрібні екрани

Роботи мало, але без них не зняти `Admin.css`:

- **Логін і Реєстрація** — форма по центру на `--ds-bg`, картка на `--ds-surface`,
  вордмарк зверху. Помилка входу — текстом під полем, не `alert`.
- **Мій кабінет** (`/admin/profile`) — дві секції: `Особисті дані` і `Змінити пароль`.
  Додати поле поточного пароля (зараз його немає) і показати роль та підрозділ
  користувача — це єдиний екран «про мене» без жодного контексту прав.
- **Форма заявки оренди** (`/admin/rental-applications/:id`) — маршрут лишався живим
  заради конвертації броні з календаря. Правильне рішення — закрити його: бронь
  конвертується одразу в угоду, а форма видаляється разом із маршрутом. Якщо це
  виявиться більшою зміною, ніж виглядає, — перевести екран на токени й лишити,
  але тоді записати в `04-release.md` як борг.

### 9.3 Фініш

Після 9.1 і 9.2 жоден файл не має імпортувати `pages/admin/Admin.css` —
перевірити grep'ом і видалити файл разом з `components/admin/AdminComponents.css`.
Потім увімкнути `@media (prefers-color-scheme: dark)` у `tokens.css` і пройтись по
всіх екранах у темній темі: шукати місця, де колір заданий літералом, а не токеном.

## 10. Прибирання

Виконати, коли всі екрани готові:

1. Перевірити, що жоден файл не імпортує `pages/admin/Admin.css` — видалити файл
   (робиться в 9.3, коли Робочий стіл і дрібні екрани готові).
2. Те саме для `components/admin/AdminComponents.css` і старих
   `components/admin/AdminTable|AdminModal|AdminFilters|AdminPageHeader|ConfirmDialog`,
   якщо їх замінили аналоги з `features/admin/ui`.
3. Увімкнути `@media (prefers-color-scheme: dark)` у `tokens.css` (зараз навмисно
   вимкнено, поки живий світлий `Admin.css`).
4. Прибрати з `services/api.js` те, що не викликається: `currenciesApi`,
   `inventoryApi.get/create/update/remove/events`, `warehousesApi.get/update/remove`,
   `subdivisionsApi.get/members`, `usersApi.get`,
   `rentalCalendarApi.listBookings/getBooking/removeBooking`, `timesheetApi.save/remove`.
   Перед видаленням переконатись, що новий код їх не використав.

## Модель даних — міграції, які точно потрібні

1. **`Product.trackingMode`** `enum('serial','quantity')`, за замовчуванням `serial`.
   Для `quantity` серійний номер необов'язковий і не потрапляє в акт; у календарі
   така позиція — один рядок зі шкалою завантаження. Проставити `quantity` для лісів
   і опалубки.
2. **`Seller`** — нова таблиця з довідником юросіб-орендодавців, дані з
   `src/constants/sellers.js` і `server/constants/sellers.js`.
3. **`BlogPost.status`** `enum('draft','published')`, за замовчуванням `published`
   для наявних записів.
4. Агрегати для списків (кількість угод і оборот клієнта, тип угоди, назва товару в
   події календаря) — обчислювані поля у відповідях, не нові колонки.

Це мінімум, а не межа. Інші зміни схеми теж дозволені — за протоколом вище
(локальна база, бекап, знімок, `down`, підтвердження перед продакшеном).

Кожна міграція — окремим файлом у `server/migrations` за наявним іменуванням, з
`down`, що коректно відкочується.
