## AdminLayout.jsx → каркас всех `/admin/*`

**Что это:** Сайдбар-оболочка админки: навигация по ролям, ролевой роут-гард, топбар с хлебными крошками и ссылкой в кабинет.

**Данные:** `useAuth()` (user.role, user.isSubdivisionHead, name/lastName/email). Собственных запросов нет.

**Действия пользователя:**
- Логотип-ссылка на `/admin`.
- Пункт `Дашборд` → `/admin`.
- Пункт `Замовлення та оренда` → `/admin/orders` (виден при shop- или rent-доступе).
- Секция `Оренда`: `Клієнти` → `/admin/clients`; `Каталог інструментів` → `/admin/rent`; `Склад` → `/admin/warehouses`.
- Пункт `ПАН ПІВДЕНЬБУД` → `/admin/pan-pivdenbud` (видим при `canUseTimesheet`).
- Секция `Магазин`: `Товари` → `/admin/products`; `Блог` → `/admin/blog`.
- Секция `Підприємство` (только `owner`): `ПАН ПІВДЕНЬБУД`, `Користувачі`, `Підрозділи`, `Налаштування`.
- `На сайт` → `/` (title `Перейти на сайт`).
- `Вийти` — logout + редирект на `/admin/login`.
- Топбар: бейдж роли + `Мій кабінет` → `/admin/profile`.
- Автоматический редирект при заходе на запрещённый путь: rent-only → `/admin/rent`, shop-only → `/admin/products`, иначе `/admin`.

**Состояния/статусы (роли, `utils/adminRoles.js`):**
- `owner` → `Власник`; `shop_manager` → `Менеджер магазину`; `rent` → `Менеджер оренди`; `pivdenbud` → `ПАН ПІВДЕНЬБУД`; `shop_rent` → `Менеджер магазину та оренди`; `manager` → `Менеджер (застаріла)`.
- Доступ: shop = owner/shop_manager/shop_rent/manager; rent = owner/rent/pivdenbud/shop_rent; табель = pivdenbud/shop_manager/shop_rent **или** `isSubdivisionHead`; «наблюдатель табеля» = только owner.

**Проблемы UX:**
- Секция «Підприємство» дублирует пункт `ПАН ПІВДЕНЬБУД`, который уже выводится выше отдельным пунктом — у owner он в меню дважды.
- `ПАН ПІВДЕНЬБУД` — одновременно название роли, название подразделения-юрлица и название пункта меню с табелем. Три разных смысла у одного термина.
- Гард в `useEffect` (после рендера), т.е. запрещённая страница на миг успевает отрисоваться.
- Хлебные крошки строятся по хардкод-мапе `getPageTitle`, для неизвестного пути отдают пустую строку.
- `RENT_PATHS` содержит `/admin/rental-applications`, который на верхнем уровне уже редиректит на `/admin/orders?tab=rental` — мёртвый префикс в гарде.

## AdminDashboard.jsx → `/admin`

**Что это:** Стартовый дашборд; для rent-only ролей полностью подменяется на `RentDashboard`.

**Данные:** `productsApi.list()` (магазин), `ordersApi.list()`, `productsApi.list({ isRent:true, includeHiddenRent:true })`.

**Действия пользователя:**
- Блок `Магазин`: карточки `Товарів у магазині`, `Замовлень`, `Загальна виручка` (не кликабельны).
- Блок `Оренда інструменту`: `Всього інструментів`, `Доступні зараз`, `Буде доступно`, `У закупівлі`, `Потребує ремонту`, `На ремонті`, `Мало на складі (≤2 шт)` (карточка появляется только при lowStock > 0).
- Карточка-ссылка `Заявки оренди` со значением `Переглянути →` → `/admin/rental-applications` (редиректится на `/admin/orders?tab=rental`).
- Таблица `Останні замовлення` (5 шт., колонки `ID`, `Клієнт`, `Сума`, `Статус`) + ссылка `Всі замовлення →` → `/admin/orders`. Строки не кликабельны.

**Состояния/статусы:** заказы — `pending` `Очікує`, `processing` `В роботі`, `completed` `Виконано`, `cancelled` `Скасовано` (**обратите внимание — здесь `pending` = «Очікує», а не «Новий», как везде; нет `invoice_sent` и `paid`**). Аренда — `in_stock/available` `Доступний`, `available_later` `З <дата>`, `in_procurement` `У закупівлі`, `needs_repair` `Потребує ремонту`, `in_repair` `На ремонті`, иначе `Недоступний`.

**Проблемы UX:**
- Три независимые реализации статуса заказа с расходящимися подписями (здесь / `AdminOrders` / `AdminClientDetails`).
- Карточки-метрики некликабельны, кроме одной — непредсказуемо, где можно «провалиться».
- Считает выручку по всем заказам без фильтра статуса (отменённые тоже входят).
- Дашборд грузит **весь** список товаров и заказов на клиент только ради подсчёта количеств.

## RentDashboard.jsx → `/admin` (подмена для ролей rent/pivdenbud)

**Что это:** Дашборд арендного менеджера: сводка по статусам инструмента + плоская таблица всего склада.

**Данные:** `productsApi.list({ isRent:true, includeHiddenRent:true })`, локально фильтрует `quantityAvailable > 0`.

**Действия пользователя:**
- Карточки: `Всього інструментів`, `Доступні зараз`, `Буде доступно`, `У закупівлі (на папері)`, `Потребує ремонту`, `На ремонті`, `Мало на складі (≤2 шт)`.
- Заголовок секции `Склад інструментів` + кнопка `Додати інструмент` → `/admin/rent/new`.
- Таблица (`Назва`, `Категорія`, `Ціна / доба`, `На складі`, `Статус`, `Дії`); в `Дії` — текстовая ссылка `Редагувати` → `/admin/rent/:id`.
- Пустое состояние: `Інструментів поки немає.` + ссылка `Додати перший`.

**Состояния/статусы:** `Доступний`, `З <дата>`, `У закупівлі (на папері)`, `Потребує ремонту`, `На ремонті`, `Недоступний`. Подсветка строки `#fff7ed` при `quantityAvailable ≤ 2`.

**Проблемы UX:**
- Полный клон карточек из `AdminDashboard`, но подпись `У закупівлі (на папері)` против `У закупівлі` — расхождение.
- Нет поиска, фильтров и пагинации — таблица без ограничения длины.
- Загружает скрытые из каталога карточки (`includeHiddenRent`), но потом отбрасывает всё с нулевым остатком: пользователь не может понять, почему инструмент «пропал».
- Дублирует `AdminRent` (тот же список, другие колонки и другие фильтры).

## AdminWarehouseHome.jsx → `/admin/warehouses` (index)

**Что это:** Обзорная страница склада: KPI аренды, карточки складов, что сейчас в аренде, лента последних событий.

**Данные:** `warehouseApi.dashboard({ eventLimit: 12 })` → `{ events, productLocations, warehouseSummary, rentSummary }`. Есть локальный фоллбэк-пересчёт `rentSummary` из `productLocations`, если сервер не отдал агрегат.

**Действия пользователя:**
- Заголовок `Склад` / `Огляд складів, активних заявок і останніх подій` + кнопка `Позиції на складі →` → `/admin/warehouses/positions`.
- KPI-карточки (нажатий нет): `Потребує ремонту`, `Всього інструменту`, `Доступно зараз`, `Знаходяться в оренді`.
- Секция `Склади`: карточка каждого склада (`Позицій:`, `Кількість:`, `Резерв:`) — клик ведёт на `/admin/warehouses/positions?warehouseId=<id>`, title `Перейти до складу «<name>»`.
- Секция `У активній оренді`: карточки товаров с их активными заявками; номер заявки — ссылка на `/admin/rental-applications/:id`; пусто → `Наразі немає товарів у заявках.`
- Секция `Останні події` + кнопка `Всі події →` → `/admin/warehouses/events`; пусто → `Подій ще немає.`

**Состояния/статусы (аренда):** `active` `Активна`, `booked` `Заброньовано`, `overdue` `Прострочено`, `returned` `Повернено`, `draft` `Чернетка`.

**Проблемы UX:**
- Ссылки на `/admin/rental-applications/:id` из карточек — маршрут заявки, тогда как основной рабочий экран сделки теперь `/admin/orders/:id` (DealWorkspace). Две точки входа в одну сущность.
- `Всього інструменту` здесь vs `Всього інструментів` в дашбордах — расхождение подписи для одной метрики.
- KPI по аренде дублируют `RentDashboard` и `AdminDashboard`, но набор метрик третий по счёту (нет «У закупівлі», «Буде доступно», зато есть «Знаходяться в оренді»).
- Событие форматируется тремя разными способами (`message` / `move_warehouse` / `send_repair` / fallback) — фид неоднородный.

## AdminWarehousePositions.jsx → `/admin/warehouses/positions` (крупнейший экран)

**Что это:** Основной рабочий стол склада: остатки по выбранному складу + инлайн-редактирование количеств + массовые перемещения + экспорт + управление складами.

**Данные:** `warehousesApi.list()`, `inventoryApi.list({ warehouseId })` (клиентски фильтрует `Product.isRent`), `inventoryApi.suggest({ q, warehouseId })`, `inventoryApi.updateItem(id, patch)`, `inventoryApi.move(...)`, `productsApi.update(id, { showInRentCatalog })`, `warehousesApi.create(...)`, `warehousesApi.requestDelete(id)`. Плюс PDF через `jspdf` + `jspdf-autotable` и загрузка шрифтов `/fonts/Roboto-Regular.ttf`, `/fonts/Roboto-Bold.ttf`.

**Действия пользователя (исчерпывающе):**

*Тулбар:*
- `Склади` — открывает модалку выбора склада.
- `Створити склад` — открывает модалку `Новий склад`.
- `Створити товар` — переход на `/admin/rent/new?returnTo=/admin/warehouses/positions&warehouseId=<id>`.
- `Експорт PDF` — landscape A4 «Склади · Звіт по залишках»; шапка `Склад:`, `Сформовано:`, `Позицій:`; колонки `Товар, SKU, Категорія, Бренд, Статус, К-сть, Резерв, Мін., Всього`; имя файла `sklad_<name>_<YYYY-MM-DD>.pdf`. Кнопка disabled при пустой выдаче.
- Плашка `Активний склад: <name>` + пометка ` (неактивний)`.

*Поиск и фильтры:*
- Поле `Пошук по назві, SKU, категорії, бренду` (placeholder `Почніть вводити...`), фильтрация клиентская.
- Кросс-складские подсказки (только когда на текущем складе ничего не нашлось, запрос дебаунс 260 мс, от 2 символов): заголовок `Можливо ви шукаєте:`, элементы вида `<товар> — склад «<склад>» · N шт. (рез. M)`, клик переключает активный склад и подставляет название; состояния `Шукаю по інших складах…` и `Нічого не знайдено в інших складах`.
- Селект `Статус`: `Усі`, `Доступний`, `Буде доступно з дати`, `У закупівлі`, `Потребує ремонту`, `На ремонті`, `Немає в наявності`.
- Селект `Категорія`: `Усі` + значения из данных.
- Селект `Бренд`: `Усі` + значения из данных.
- Селект `У каталозі`: `Усі` / `Так` / `Ні`.
- Кнопка `Скинути фільтри` (появляется только при активных фильтрах; текстовый поиск ею не сбрасывается).

*Таблица (12 колонок):* чекбокс-«всё», раскрывашка, `Товар`, `Ціна / доба`, `Тип / бренд`, `Статус`, `У каталозі`, `Всього од.`, `К-сть`, `Резерв`, `Мін.`, `Дії`.

Створіть перший через «Створити склад».`

*Модалка `Новий склад`:* поля `Назва складу` (placeholder `Наприклад: Склад №2`), `Нотатки` (placeholder `Опціонально`); кнопки `Скасувати` и `Створити склад` / `Збереження...`. Поле `isActive` есть в состоянии формы, но в UI не выведено.

*Массовые действия (плавающая панель при выделении):*
- `Обрано: N`.
- `Перемістити обрані` — модалка `Перемістити обрані товари`, подзаголовок `Зі складу: <name>`, селект `Склад призначення`, кнопка `Перенести все (по всіх товарах)`, построчные инпуты количества с подписью `На складі: N шт.`, кнопки `Скасувати` и `Перемістити` / `Переміщення…`. Валидация: `Некоректна кількість для «<товар>»`.
- `Очистити вибір`.

**Состояния/статусы (`stockStatusLabel`, вычисляемые):**
- `needs_repair` → `Потребує ремонту`; `in_repair` → `На ремонті`; `out_of_stock` → `Немає в наявності`.
- Если `quantityAvailable ≤ 0` и статус не из перечисленных: `В оренді` (если на складе есть кол-во) либо `Немає вільних`.
- `available`/`in_stock` → `Доступний`; `available_later` → `З <дата>`; `in_procurement` → `У закупівлі (на папері)`.
- Цветовые пилюли: `--ok`, `--soon`, `--repair`, `--inrepair`, `--danger`, `--procurement`, `--rented`, `--muted`.

**Проблемы UX:**
- **12 колонок**, часть из которых — инпуты; горизонтальный скролл на любом экране.
- Три соседние числовые колонки `К-сть` / `Резерв` / `Мін.` без пояснений; `К-сть` требует подтверждения, а `Резерв` и `Мін.` сохраняются молча — непоследовательно и опасно.
- `Всього од.` (это `quantityAvailable` по всем складам) стоит рядом с `К-сть` (на текущем складе) — постоянный источник путаницы.
- Ключевые действия спрятаны в модалке `Робота з товаром`: редактирование карточки, возврат из ремонта, удаление со склада, связанные заявки — ничего из этого не видно из таблицы.
- Удаление склада работает не как удаление, а как «запрос на удаление» на согласование owner’у в `/admin/admin` — но об этом на экране не сказано, кнопка — просто крестик с title.
- Активный склад запоминается в `localStorage` (`admin.selectedWarehouseId`), а фильтры по колонкам и поиск — не сохраняются вовсе.
- Кнопка `Скинути фільтри` не сбрасывает текстовый поиск.
- Массовое перемещение выполняется циклом последовательных запросов: при падении на середине половина уже перемещена, отката нет.
- Ошибки — через `alert()` / `window.confirm()`, при том что в проекте есть `ConfirmDialog` и `ToastProvider`.
- Статус — гибрид ручного `stockStatus` и вычисленного `В оренді`/`Немає вільних`; из фильтра `Статус` вычисленные значения выбрать нельзя (фильтр работает только по сырому `stockStatus`).
- Кнопка `Створити товар` создаёт **арендную** карточку — из названия это неочевидно.
- Фильтрация `Product.isRent` — на клиенте, после загрузки всего инвентаря склада.

- Депозит показывается то как `liveDeposit` из заявки, то как оценка `estimateOrderDeposit` — пользователь не знает, что перед ним.
- Ошибки — `alert()`.

- Таб `Позиції`: поиск и добавление товаров, правка строк, удаление строки и удаление элемента комплекта (`onRemoveKitItem`), `Додати порожню позицію` (`addEmptyItem`), тип и величина скидки (блокируются, если скидка пришла из заказа), итоги. В режиме `enrichmentOnly` (внутри сделки) — только обогащение, без изменения коммерческих полей.
- Таб `Документ`: сводка (номер, клиент, количество позиций, сумма после скидки, залог, итог), поле `Нотатки`, кнопки скачивания заявки и акта возврата (`variant: 'return_inspection'`), кнопка печати.
- Панель `UpsellPanel` (вне режима `enrichmentOnly`) — предложение сопутствующих позиций при добавлении товара, с закрытием и добавлением.
- Скрытый блок `RentalApplicationPrint` — печатная форма.
- Загрузка → `Завантаження заявки...`.

**Состояния/статусы:** `STATUS_SELECT_OPTIONS` из `model/rentalStatus` (файл не в выгрузке); отображаемый набор совпадает с `STATUS_META` (`Чернетка`, `Заброньовано`, `Активна`, `Прострочено/Термін прострочено`, `Повернено/Повернуто`, `Скасована`).

**Проблемы UX:**
- Компонент имеет **семь** булевых пропов-переключателей режима (`embedded`, `hideHeader`, `hideToolbarSave`, `hideDocumentTab`, `hidePartiesTab`, `enrichmentOnly`, `+ discountLocked`) — фактически два разных экрана, слепленных в один; в каждом режиме пользователь видит свой набор вкладок и кнопок.
- Документы заявки формируются **здесь** (кнопки скачивания в табе `Документ`, генерация PDF на клиенте), а те же по смыслу документы — **ещё и** в `DocumentsPanel` сделки (генерация на сервере, с версионированием). Два конвейера документов.
- Внутри сделки таб `Сторони` скрыт, но данные клиента при этом редактируются в `OrderClientCard` — одно и то же поле в разных местах в зависимости от режима.
- Скидка бывает заблокирована без внятного объяснения (`discountLocked` при наличии связанного заказа).

# Дубликаты и пересечения

**1. Каталог арендного инструмента — три экрана.**
`/admin/rent` (`AdminRent`), `/admin` для rent-ролей (`RentDashboard`) и `/admin/warehouses/positions` (`AdminWarehousePositions`) показывают один и тот же набор арендных карточек с разными колонками, разными фильтрами и разными правилами отсечения (`quantityAvailable > 0` / `includeHiddenRent` / `Product.isRent` по складу).

**2. Дашборд аренды — три набора KPI.**
`AdminDashboard` (блок «Оренда інструменту»), `RentDashboard` и `AdminWarehouseHome` считают почти одинаковые метрики, но с разным составом и разными подписями (`Всього інструментів` / `Всього інструменту`, `У закупівлі` / `У закупівлі (на папері)`).

**3. Статусы заказа магазина — три независимые мапы.**
`AdminDashboard.STATUS_LABELS` (4 значения, `pending` = `Очікує`), `AdminOrders`/`OrderHeader` через `orderHelpers` (6 значений, `pending` = `Новий`), `AdminClientDetails.SHOP_ORDER_STATUS_META` (6 значений).

**4. Статусы аренды — четыре объявления.**
`AdminWarehouseHome.STATUS_RENT_LABEL`, `WarehouseProductWorkModal.STATUS_LABEL`, `AdminClientDetails.STATUS_META`, `model/rentalStatus.STATUS_META`. Подписи расходятся: `Прострочено`/`Термін прострочено`, `Повернено`/`Повернуто`.

**5. Редактирование клиента — три места.**
Модалка в `AdminClients`, модалка в `AdminClientDetails` (одинаковый набор полей, скопированный), инлайн-редакторы `Нотатки`/`Претензії` там же. Плюс создание клиента из `DealWorkspace` (`Додати`) и подстановка данных клиента в композере `AdminOrders`.

**6. Количество на складе редактируется дважды.**
Колонка `К-сть` в `AdminWarehousePositions` и поле склада/количества в `ProductEdit` (`editWarehouseQuantity`) пишут в одну величину разными путями (`inventoryApi.updateItem` vs `productsApi.update` с `editWarehouseId/Quantity`).

**7. Видимость в каталоге аренды переключается дважды.**
Кнопка `Прибрати з каталогу` / `Перевести в каталог` на складе и поле `showInRentCatalog` в `ProductEdit`.

**8. Заявка аренды редактируется в двух маршрутах.**
`/admin/rental-applications/:id` (полноэкранный `AdminRentalApplicationForm` → `RentalApplicationEditor`) и встроенно в `/admin/orders/:id`. Ссылки из склада, из карточки клиента, из календаря ведут на первый вариант; основной рабочий процесс — во втором.

**9. Документы генерируются двумя конвейерами.**
Клиентский PDF в табе `Документ` редактора заявки (`generateRentalPdf`) и серверный с версиями в `DocumentsPanel` сделки. `Заявка оренди` и `Акт повернення-огляду` существуют в обоих.

**10. Настройки и пользователи смонтированы по двум маршрутам.**
`/admin/settings` + `/admin/admin/settings` → `AdminCategories`; `/admin/users` + `/admin/admin/users` → `AdminUsers`.

**11. Категории магазина заданы дважды.**
Хардкод `CATEGORY_OPTIONS` в `AdminProducts` и справочник в `AdminCategories`/`categoriesApi`.

**12. Списки товаров грузятся целиком в четырёх местах** ради клиентского поиска/фильтрации: `AdminOrders`, `RentalCalendar`, `AdminDashboard`, `ProductEdit` (инвентарь).

**13. `ПАН ПІВДЕНЬБУД`** — одновременно роль, пункт меню/раздел табеля и юрлицо-продавец `ТОВ «ПАН-ПІВДЕНЬБУД»` в `constants/sellers.js`.

**14. `ProductEdit`** обслуживает и товар магазина, и арендный инструмент через проп `context`, при этом монтируется под двумя маршрутами и с двумя наборами хлебных крошек.

# Что мёртвое / неиспользуемое

- **`/admin/admin` и весь `AdminAdminLayout` + `AdminAdminHome`.** Ни один пункт сайдбара сюда не ведёт ни для одной роли. При этом `AdminAdminHome` — **единственное** место, где согласуются запросы на удаление складов, создаваемые с `/admin/warehouses/positions`. Функционально живой, навигационно мёртвый.
- **Легаси-редиректы в `App.jsx`** (`/admin/admin`, `/admin/admin/users`, `/admin/admin/settings` → плоские пути) объявлены **после** вложенного роута `/admin/admin` и потому никогда не срабатывают.
- **`currenciesApi`** (`list`, `update`) — не вызывается ни на одном экране; UI управления валютами отсутствует.
- **`inventoryApi.moveToRepair`** — не вызывается нигде в выгрузке. Обратная операция `restoreInStock` используется (в `WarehouseProductWorkModal`), т.е. «вернуть из ремонта» есть, а «отправить в ремонт» — нет.
- **`inventoryApi.get`, `inventoryApi.create`, `inventoryApi.update`, `inventoryApi.remove`, `inventoryApi.events`** — не используются (`events` дублируется `warehouseApi.events`).
- **`warehousesApi.get/update/remove`** — не используются; удаление идёт только через `requestDelete` + согласование.
- **`subdivisionsApi.get`, `subdivisionsApi.members`** — не вызываются.
- **`usersApi.get`** — не вызывается.
- **`rentalCalendarApi.listBookings`, `getBooking`, `removeBooking`** — не вызываются (используются `events`, `create`, `update`, `cancel`, `convert`).
- **`ordersApi.create`** (публичный) и **`ordersApi.getNextRentalActNumber`** — не вызываются из просмотренных админ-экранов.
- **`timesheetApi.save`** и **`timesheetApi.remove`** — не используются (сохранение только помесячное через `saveMonth`).
- **`AdminModal.jsx`** — переиспользуемая модалка с фокус-ловушкой, блокировкой скролла и Escape существует, но **ни один** просмотренный экран её не импортирует; все модалки написаны вручную через `admin-modal-overlay`.
- **`AdminFilters` проп `actions`** — не используется ни в одном вызове.
- **`AdminPageHeader` проп `backTo`** — не используется ни в одном вызове (везде свои кнопки «назад»).
- **`AdminTable` проп `rowKey`** — не используется.
- **Поле `isActive` в форме создания склада** (`EMPTY_FORM`) — отправляется на сервер, но в UI модалки `Новий склад` не выведено; изменить его после создания нельзя нигде.
- **`RENTAL_LESSOR` в `constants/sellers.js`** — помечен `@deprecated`, оставлен для старых импортов.
- **`ROLES.SHOP_MANAGER`-стиль роль `manager`** — числится в `ROLE_LABELS` как `Менеджер (застаріла)` и в `hasShopAccess`, но отсутствует в селекте ролей `AdminUsers`.
- **`AdminWarehousePositions`: состояние `colSpan = 12`** зафиксировано константой, тогда как реальное число колонок задаётся разметкой — рассинхронизируется при добавлении колонки.
- **`RentDashboard`** формально достижим только как подмена дашборда для rent-only ролей; прямого маршрута у него нет.
- **`/admin/rental-applications`** как страница-список более не существует — только редирект; но ссылки на неё остались в `AdminDashboard` (карточка `Заявки оренди`) и в `AdminLayout.RENT_PATHS`.

# Ключевые сущности и их связи

**Product (карточка товара) — единая таблица для магазина и аренды**
Признак `isRent` разделяет два мира. Общие поля: `id`, `name`, `slug`, `sku`, `category`, `brand`, `price`, `oldPrice`, `image`, `images`, `desc`, `instruction`, `adminNotes`, `specs`, `unit`, `packSize`, `badge`, `groupId`, `priceMatrix`, `relatedProducts`.
Только аренда: `rentPriceTiers` (4 уровня, минимальный определяет `price`), `kitItems`, `serialNumber`, `inventoryNumber`, `technicalCondition`, `weightPerUnit`, `weightTotal`, `replacementCost`, `securityDeposit`, `competitorLinks`, `adminImages`, `showInRentCatalog`, `stockStatus`, `availableFrom`, `quantityAvailable` (агрегат по всем складам).
Только магазин: `quantityAvailable` как ручное число, `badge`.
Редактируется: `ProductEdit` (оба контекста), частично — из склада (`showInRentCatalog`, косвенно остатки).

**Warehouse (склад)** — `id`, `name`, `notes`, `isActive`. Два имени особые и захардкожены в логике: `Основний склад` (нельзя запросить удаление) и `У ремонті` (включает блок «Повернути з ремонту»). Удаление — только через `requestDelete` → очередь в `/admin/admin`.

**InventoryItem (позиция на складе)** — связка `productId × warehouseId` с полями `quantity`, `reserved`, `minStock`. Именно её редактирует таблица `/admin/warehouses/positions`. Сумма/агрегат по всем складам приходит в `Product.quantityAvailable`. Перемещение — `inventoryApi.move({ productId, fromWarehouseId, toWarehouseId, quantity })`.

**WarehouseEvent (событие склада)** — `id`, `createdAt`, `userId`, `userDisplayName`, `productId`, `productName`, `action` (`move_warehouse`, `send_repair`, …), `message`, `fromWarehouseName`. Порождается перемещениями, ремонтом, правками количества/резерва. Отдельный подтип — **запрос на удаление склада** (`warehouseApi.deleteRequests` возвращает записи с теми же полями `createdAt`/`userDisplayName`/`fromWarehouseName`/`message`), т.е. очередь согласований физически живёт в том же журнале событий.

**Client (клиент)** — `id`, `fullName`, `phone` (несколько номеров в одном поле, разбираются `parsePhones`), `email`, `passport`, `passportIssuedAt`, `ipn`, `address`, `siteAddress`, `discountPercent`, `notes`, `claims`, `createdAt`. Поиск по телефону — `clientsApi.lookupByPhone`. Клиент связан с Order через `clientId` и с RentalApplication через `clientId`.

**Order (заказ / сделка)** — `id`, `orderNumber` (формат `N/дд/мм/рррр`), `status`, `customerName/Phone/Email`, `address`, `deliveryMethod`, `paymentMethod`, `discount`, `totalAmount`, `items[]`, `clientId`, `sellerId`, `rentStartTime`, `rentalApplicationId`, `createdAt`. Позиция (`item`): `id` (productId), `name`, `sku`, `price`, `quantity`, `unit`, `packSize`, `isRent`, `rentFrom`, `rentTo`, `rentDays`. Заказ считается арендным, если хотя бы одна позиция арендная (`orderHasRentItems`), и магазинным — если есть неарендная; может быть и тем и другим одновременно.

**RentalApplication (заявка аренды)** — `id`, `applicationNumber`, `status`, `clientId`, `clientName/Phone/Email/Passport/Address/SiteAddress`, `responsible[]` (`{name, phone}`), `items[]` (с `productId`, `rentFrom`, `rentTo`, серийниками, состоянием, комплектом), `rentFrom`, `rentTo`, `discountType`, `discountValue`, `totalAmount`, `depositAmount`, `notes`, `linkedOrder`. Создаётся из заказа (`POST /api/orders/:id/rental-application`) либо из брони календаря (`convertBooking`), либо вручную (`/admin/rental-applications/new`). Заявка — «обогащение» заказа: коммерческие условия приходят из заказа, а заявка добавляет серийные номера, состояние, комплект и залог.

**RentalCalendarBooking (бронь)** — `id`, `productId`, `rentFrom`, `rentTo`, `clientName`, `clientPhone`, `note`. Отдельная лёгкая сущность «до заявки». Календарь отдаёт унифицированные события с `source: 'booking' | 'application'` и `kind` для окраски. Бронь конвертируется в RentalApplication.

**Document (документ заказа)** — `id`, `type`, `title`, `fileName`, `createdAt`. Типы: `invoice`, `deposit_invoice`, `rental_application`, `rental_return_act`, `rental_contract`, `rental_protocol`, плюс `other`. Привязан к Order, версионируется (несколько документов одного типа, сортировка по дате). Договор и протокол имеют предварительную проверку (`/check`), возвращающую список недостающих полей.

**Seller / Lessor (продавец-арендодатель)** — статический реестр в `constants/sellers.js`: 4 юрлица (`fop_pankratiev_mo` — по умолчанию, `fop_pankratiev_mykhailo`, `fop_pankratiev_om`, `tov_pan_pivdenbud`), у каждого блок `rentalLessor` (имя, ІПН, адрес) и общие офисные контакты. Выбирается на заказе (`sellerId`), влияет на печатные формы, на расчёт ПДВ (`appliesVat`, `billingOptions`) и на блок «Сторони» в заявке.

**User (пользователь админки)** — `id`, `name`, `lastName`, `email`, `role`, `status`, `isSubdivisionHead`. Роль определяет и меню, и доступные маршруты, и режим табеля.

**Subdivision (подразделение)** — `id`, `name`, `head` (обязательно User с аккаунтом), `members[]` (либо `{userId}`, либо `{displayName}` — «сотрудник без аккаунта», существующий только как строка табеля), максимум 30 участников. Один пользователь — максимум в одном подразделении. Удаление подразделения понижает роль головы с `pivdenbud` до `rent`.

**TimesheetEntry (запись табеля)** — `year`, `month`, `day`, `slot` (номер строки-сотрудника), `arrivalHour`, `arrivalMinute`, `departureHour`, `departureMinute`. Сохраняется пачкой за месяц (`saveMonth`). Владелец табеля — голова подразделения; owner получает агрегат `overview` в виде `sheets[]` (`headUserId`, `subdivisionName`, `headDisplayName`, `headEmail`, `labels[]`, `entries[]`).

**Category / RentCategory / Brand (справочники)** — `Category`: `name`, `slug`. `RentCategory`: `name`, `slug`, `group` (свободный текст), `isActive` (видимость на сайте). `Brand`: `name`, `logo`, `isShop`, `isRent`.

**BlogPost** — `id`, `title`, `category`, `image`, `date`.

**Схема связей (как её подразумевает код):**

```
User ──head/member──> Subdivision ──> TimesheetEntry (slot = строка сотрудника)
User ──author──> WarehouseEvent

Category ─┐
Brand ────┼──> Product ──isRent?──┬── магазин: AdminProducts / ProductEdit
RentCategory ─┘                   └── аренда: AdminRent / ProductEdit(context=rent)

Product ──1:N──> InventoryItem ──N:1──> Warehouse
       (quantity, reserved, minStock)         │
                                              └──> WarehouseDeleteRequest ──> /admin/admin

Client ──1:N──> Order ──1:N──> OrderItem(productId, rentFrom/rentTo)
  │              │
  │              ├──1:1──> RentalApplication ──1:N──> RentalApplicationItem(productId, серийники, комплект)
  │              │                    ▲
  │              │                    └──convert── RentalCalendarBooking(productId, даты)
  │              │
  │              ├──1:N──> Document (invoice / deposit_invoice / rental_application /
  │              │                   rental_return_act / rental_contract / rental_protocol)
  │              └──sellerId──> Seller.rentalLessor (печатные формы, ПДВ)
  │
  └──1:N──> RentalApplication (напрямую, для заявок без заказа)
```

Узкое место модели: **Product ↔ InventoryItem ↔ Order/RentalApplication связаны только по `productId`, без резервирования конкретных единиц.** Отсюда вычисляемые псевдостатусы `В оренді` / `Немає вільних` на складе, поле `reserved`, редактируемое вручную, и невозможность в одном месте увидеть, где физически находится конкретная единица инструмента: карточка знает агрегат, склад — количество на складе, заявка — что выдано клиенту, и эти три числа никогда не сверяются автоматически.
